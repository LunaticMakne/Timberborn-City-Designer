# Timberborn City Designer — 프로젝트 플랜

상태: 대화에서 합의한 방향을 정리한 초안. 미정 항목은 구현 전에 해당 단계에서 결정한다.

다음 단계 설계안: [설치본 기반 실제 건물 카탈로그](superpowers/specs/2026-09-30-live-catalog-design.md). 전체 데이터 확보 후 기본 건물군을 연결하는 범위는 합의했으며, 저장 호환성·표시 정책을 포함한 문서는 검토 대기 중이다.

현재 진행: 사용자 요청에 따라 레이아웃과 배치·탐색 체험을 먼저 구현한다. 사용 중 피드백에 따라 기본 겹침·경계 검사는 지금 적용하고, 지지·출입구·연결 등 게임별 검증은 후속 구현으로 미룬다. 화면에 사용하는 예시 오브젝트의 치수는 실제 게임 데이터로 간주하지 않으며, 게임 정보 확인은 실제 카탈로그를 연결할 때 진행한다.

배치 조작 피드백 반영: 고정 높이 평면만 사용하는 방식에서, 마우스로 가리킨 건물·플랫폼 윗면의 높이를 읽어 배치하는 방식으로 개선한다. 고정 높이 배치는 Shift로 유지한다. 미리보기와 저장되는 좌표는 같은 레이캐스팅 결과를 사용한다. 이는 배치 조작의 개선이며 배치 규칙 검증을 앞당기는 변경은 아니다.

방향 확인 피드백 반영: 배치 미리보기는 점유 공간 상자 대신 배치 후와 같은 표시 모델을 반투명하게 사용한다. 정면 표시와 회전 각도를 함께 보여 주어 정사각형 오브젝트도 배치 전에 방향을 확인할 수 있게 한다. 설계 파일의 좌표·회전 규약은 그대로 유지한다.

복제 높이 피드백 반영: 원본 층을 복제 배치의 하한으로 사용하지 않는다. 자동 배치는 종류·방향을 유지하면서 커서가 가리킨 표면 또는 바닥 0층을 따르고, 지정 높이 고정은 Shift를 누른 동안만 적용한다. 층 보기와 자동 배치 높이가 서로를 제한하지 않게 한다.

겹침 방지 피드백 반영: 겹쳐서 지을 수 없는 배치를 가능한 것으로 오해하지 않도록, 회전된 점유 직육면체의 겹침과 격자 경계를 검사한다. 미리보기에서 빨간색과 이유를 표시하고 새 배치·좌표 변경·회전·파일 불러오기를 막는다. 복제는 둘 위치를 고르는 방식으로 동작한다. 기존 브라우저 저장본은 삭제하지 않고 문제를 표시해 수정하게 한다. 게임 건설 규칙은 미검증임을 계속 표시한다.

카메라 조작 피드백 반영: 브라우저 마우스 제스처와 충돌하는 우클릭 이동을 제거하고, 화면 방향 기준 WASD 연속 이동을 사용한다. 배치 중에도 사용할 수 있으며 입력창·도움말·창 포커스 이탈 시에는 이동을 중단한다. 선택 도구의 왼쪽 드래그 회전과 휠 확대·축소는 유지한다.

이동 속도 피드백 반영: 기존 WASD 속도를 최저·기본값인 1×로 유지하고 줌 버튼 옆 슬라이더에서 3×까지 0.25× 단위로 조절한다. 즉시 반영하며, 청사진 데이터와 별도로 브라우저에 보관한다.

## 1. 만들려는 도구

게임 옆에 웹 페이지를 띄워 두고, Timberborn의 실제 게임 오브젝트를 배치하며 메가시티 청사진을 설계하는 개인용 도구다. 사용자는 웹에서 배치를 시험하고 여러 각도와 층에서 확인한 뒤, 게임에서 설계를 보며 직접 건설한다.

설계에 필요한 부지 크기와 배치를 먼저 정하고, 실제 게임의 지형은 필요하면 그 설계에 맞춰 평탄화한다. 따라서 초기 설계 공간은 평평한 타일 격자로 시작하며, 실제 지형이나 세이브를 준비하지 않아도 사용할 수 있어야 한다.

AI 에이전트는 설계 데이터를 직접 읽고 수정한다. 웹 화면과 에이전트는 같은 설계 데이터를 사용하며, 사람이 배치한 결과와 AI가 수정한 결과를 서로 이어서 작업할 수 있어야 한다.

대상 게임은 현재 라이브 버전이다. 사용자는 설계할 진영을 선택할 수 있어야 하며, 선택한 진영에 맞는 게임 오브젝트를 배치한다. 오브젝트 정보를 확인할 때 기준이 된 구체적인 게임 버전도 기록한다.

## 2. 핵심 사용 흐름

1. 진영을 선택해 새 청사진을 만들거나 저장된 청사진을 연다.
2. 게임 오브젝트를 선택하고 타일 격자 위에 배치한다.
3. 위치, 방향, 높이를 조정하며 도시를 구성한다.
4. 전체를 둘러보거나 위층을 숨겨 특정 층과 내부 배치를 확인한다.
5. 필요하면 에이전트와 대화하며 설계의 일부를 읽고 수정한다.
6. 결과를 웹에서 확인하고 저장한다.
7. 게임 옆에서 층별 청사진을 보며 직접 건설한다.

## 3. 첫 사용 가능한 버전의 범위

- 평평한 타일 격자에서 설계한다.
- 진영을 선택할 수 있고, 해당 진영에 맞는 오브젝트 목록을 사용한다.
- 실제 게임 오브젝트 중 확인된 소수 종류를 배치할 수 있다. 건물과 플랫폼·계단처럼 여러 층의 배치를 확인할 수 있는 구성을 우선 검토한다.
- 배치된 오브젝트를 선택하고 이동, 회전, 높이 변경, 삭제할 수 있다.
- 카메라를 회전, 이동, 확대·축소할 수 있다.
- 층을 선택하거나 위층을 숨겨 내부를 살펴볼 수 있다.
- 청사진의 가로·세로 범위와 높이를 확인할 수 있다.
- 설계를 저장하고 다시 열어 같은 배치를 복원할 수 있다.
- 외부 에이전트가 설계 데이터의 일부를 읽고 수정한 결과를 웹에서 확인할 수 있다.

게임의 그래픽을 재현할 필요는 없다. 단순한 블록이나 기본 도형으로 표시하되, 배치에 필요한 실제 점유 크기와 방향을 읽을 수 있어야 한다. 표시가 단순하다는 이유로 서로 다른 게임 오브젝트를 같은 의미의 상자로 취급하지 않는다.

완료 기준은 작은 다층 청사진을 직접 만들고 저장한 다음, 에이전트로 일부 배치를 수정하고, 다시 웹에서 층별로 확인하는 흐름이 이어지는 것이다. 게임에서 따라 지어 보는 사용자 피드백으로 실제 유용성을 확인한다.

## 4. 설계 데이터와 AI 협업 원칙

설계 데이터는 화면 상태와 별개로 이해할 수 있어야 한다. 화면 인식 없이도 어떤 오브젝트가 어디에 어떤 방향으로 놓였는지 알 수 있어야 한다.

다음 역할을 구분한다. 파일 개수와 저장 형식은 아직 정하지 않는다.

- **오브젝트 정의:** 게임 오브젝트의 종류, 확인된 점유 공간, 출입구 등 배치에 필요한 정보와 그 근거.
- **청사진:** 선택한 진영과 배치별 고유 식별자, 오브젝트 종류, 위치, 높이, 방향 등 사용자가 설계한 내용.
- **보기 설정:** 카메라와 현재 표시하는 층 등 화면을 보는 데 필요한 상태.

에이전트가 특정 층, 좌표 범위 또는 식별자로 필요한 배치만 읽고 수정할 수 있도록 구성한다. 이 기능을 파일 구성으로 제공할지, 작은 도구로 제공할지는 데이터 규모와 실제 사용을 보고 정한다. 대도시 전체 데이터를 매 요청마다 전달하는 방식을 전제로 삼지 않는다.

웹과 에이전트가 동일한 좌표·방향·오브젝트 정의를 해석해야 한다. 구체적인 형식과 함께 좌표축, 높이 기준, 회전 기준을 문서화한다. 확인하지 못한 게임 규칙은 추측으로 확정하지 않고 미확인 상태를 드러낸다.

에이전트가 바꾼 설계를 다시 불러오는 방법과 기존 편집을 덮어쓰지 않는 방법도 정해야 한다. 초기에는 명시적인 저장·불러오기처럼 단순한 방식을 우선 검토한다. 웹 내부 AI 대화창이나 특정 AI 서비스 연결은 핵심 데이터 편집 흐름과 별도로 판단한다.

## 5. 개발 순서와 단계별 완료 기준

### 선행 작업 — 화면과 조작 확인

예시 오브젝트와 청사진으로 라이브러리, 3D 작업 공간, 속성 패널, 층 조절의 레이아웃을 만들고 배치·탐색 흐름을 체험한다. 창을 게임 옆에 좁게 띄웠을 때의 사용성도 확인한다. TypeScript·Vite·Three.js를 사용한 작은 로컬 웹 앱으로 시작한다.

기본 배치, 속성 변경, 층 숨김과 JSON 저장·불러오기에 겹침·경계 검사를 연결한다. 진영별 실제 건물 카탈로그와 게임별 상세 배치 검증은 이후에 연결한다. 이 선행 작업은 아래 단계 전체를 완료했다는 의미가 아니며, 실제 게임 치수에 근거한 설계 도구로 전환하기 위한 화면 검토 단계다.

완료 기준: 사용자가 예시 화면을 직접 조작하며 레이아웃과 흐름에 대한 피드백을 줄 수 있다.

### 단계 1 — 최소 오브젝트 범위와 데이터 규약

현재 라이브 버전을 확인하고, 진영 선택을 지원하는 데 필요한 공통·진영별 오브젝트 정보와 첫 오브젝트 목록을 정리한다. 필요한 크기와 방향 정보는 실제 게임이나 확인 가능한 자료를 사용하며 치수를 추측하지 않는다.

그 범위를 표현하는 최소 설계 데이터와 예시 청사진을 만든다. 웹과 에이전트가 같은 데이터를 다루도록 식별자, 좌표, 회전, 저장 형식을 정한다. 이때 필요한 수준에서 기술 스택도 선택한다.

완료 기준: 예시 청사진만 읽어도 오브젝트의 종류와 배치를 재구성할 수 있고, 오브젝트 정의의 확인된 내용과 미확인 내용을 구별할 수 있다.

### 단계 2 — 웹 배치와 탐색의 기본 흐름

평평한 격자와 단순한 3D 표현을 만들고, 오브젝트 배치·선택·이동·회전·높이 변경·삭제, 카메라 조작, 저장·불러오기를 연결한다.

완료 기준: 웹에서 작은 배치를 만들고 여러 방향에서 확인한 뒤, 저장한 파일을 다시 열어 같은 배치를 복원한다.

### 단계 3 — 다층 청사진을 읽는 흐름

층 선택과 위층 숨김, 좌표·크기 확인을 추가하고, 플랫폼·계단 등을 포함한 예시로 내부 배치가 읽히는지 점검한다. 여러 층에 걸친 오브젝트의 표시 방식도 이 단계에서 정한다.

완료 기준: 사용자가 게임 옆에 화면을 두고 각 층에서 무엇을 어디에 놓을지 확인할 수 있다.

### 단계 4 — 에이전트와 실제로 설계 주고받기

초기부터 마련한 데이터 규약을 사용해, 에이전트가 설계 일부를 조회하고 변경한 뒤 웹으로 되돌리는 흐름을 검증한다. 필요한 경우 범위 조회나 부분 수정용 작은 도구를 추가한다.

완료 기준: 특정 오브젝트 이동이나 일부 층의 수정 요청을 데이터만으로 수행하고, 변경 대상 외의 배치를 유지한 채 웹에서 결과를 확인한다. 변경을 되돌릴 방법도 확인한다.

### 단계 5 — 실제 메가시티 설계로 확장

실제 사용 중 반복되는 작업과 규모상의 문제를 근거로 오브젝트 종류, 편집 기능, 성능을 확장한다. 영역 표시, 묶음 편집, 복제, 치수 표시와 배치 규칙 검증 등의 우선순위는 이때의 피드백으로 정한다.

완료 기준: 사용자가 만들려는 도시 규모에서 설계를 편집하고 탐색할 수 있다. 구체적인 오브젝트 수와 성능 목표는 실제 청사진 규모가 확인되면 정한다.

이 단계들은 큰 작업 순서다. 각 단계에 착수할 때 필요한 작은 작업과 검증 방법을 구체화한다.

## 6. 뒤로 미루는 범위

- 실제 맵 지형과 세이브 불러오기.
- 자유로운 영역 표시나 구역의 용도를 나타내는 보조 블록.
- 게임의 모든 건물과 모든 배치·연결 규칙 지원.
- 자원 생산, 동선, 전력·수리 등의 게임 시뮬레이션.
- 웹 내부 AI 대화창, 자동 설계 최적화 등 추가 기능.

세이브 연동을 진행할 때는 실제 `.timber` 파일을 먼저 분석한다. 실제 세이브에서 읽은 도시와 사용자가 만든 미래 계획은 구분한다. 게임 자동 플레이와 세이브에 도시를 주입하는 기능은 프로젝트 목표에 포함하지 않는다.

## 7. 아직 결정하지 않은 사항

- 진영별로 처음 지원할 오브젝트 종류와 정보 확보 방법.
- 초기 단계에서 표시만 할 게임 규칙과 실제로 검사할 규칙의 범위.
- 설계 파일 형식, 좌표 규약, 웹 편집과 외부 편집 결과를 주고받는 방식.
- 웹 UI·3D 렌더링 기술, 로컬 실행과 배포 방식.
- 되돌리기, 복제, 묶음 편집 등 편집 편의 기능의 도입 시점.
- 지원할 청사진 규모와 성능 목표.

결정되지 않은 항목을 모두 먼저 확정하지 않는다. 해당 단계에 필요한 선택을 사용자와 논의한 뒤 이 문서에 반영한다.

## 8. 진행과 피드백 반영

큰 설계 결정은 사용자와 맞춘 뒤 진행한다. 각 단계에서 확인된 사실, 미정 사항, 다음 작은 작업, 사용자 선택이 필요한 부분을 간단히 공유한다.

사용자가 실제 게임에서 확인한 정보나 사용 중 피드백을 주면, 단순히 화면만 고치는 데 그치지 않고 오브젝트 정의, 설계 데이터, 기존 청사진과 다음 개발 단계에 미치는 영향을 함께 검토한다. 필요한 경우 이 플랜의 순서와 완료 기준도 갱신한다.

GitHub에는 `main`만 유지한다. 구현 작업은 필요에 따라 로컬 작업 브랜치나 worktree에서 진행하고 검증된 결과를 `main`에 반영한다.
